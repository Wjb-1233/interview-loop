## 3. 有意保留的设计

### 功能域单体、共享训练模型：保留

文字、语音和视频最终进入 `TrainingSession / Message / Evaluation`，复用评分与提升流程。实时传输不同，持久化结果一致，这是当前系统最有价值的统一边界。没有证据表明需要拆微服务或为每种方式再建一套报告模型。

### LangGraph：保留，但准确描述能力

`backend/app/features/training/graph.py:177` 当前是 `safety → advance → prompt` 的线性图，模型调用在 service 中，未见持久化 checkpointer 或复杂自治 Agent 循环。它有明确阶段编排职责，也有毕业设计展示价值；不能把它宣传成具有断点恢复能力的多 Agent 系统。用普通函数替换可能简化依赖，但不是本轮最高收益的安全清理。

### 双语音引擎、音频恢复与权限序号：保留

`c7bdc53` 的提交正文明确记录：PCM 曾被当 JSON 丢弃、AudioContext 挂起导致麦克风无数据、ASR delta 被重复拼接。`4676c29` 记录了设备授权等待、拒绝引导与迟到结果作废。这些条件仍可能发生，不能因代码中出现重试、序号和多次 resume 就判为多余。

### 微课固定快照、缓存兼容和多级渲染/TTS 兜底：保留

`backend/app/features/plans/lesson_videos.py` 的 GET 只读取已有课程；POST 才生成并保存版本关联，防止用户回看旧计划时重新付费生成。旧视频文件名匹配也是回看保障。

Remotion 与 Python 渲染均有调用方，旁白仍按豆包 → Edge → 系统语音回退。当前实时教师换为 Live2D，并不意味着可删除 `video/`：它仍负责可保存的微课视频。语音、视频保存还使用 Whisper/MediaPipe，不能随旧上传入口一起误删相关依赖。

### 安全边界与持久化历史：保留

短期 WS 票据、令牌用途区分、对象归属、分享撤销、录制签名和删除级联都对应已有修复证据。旧迁移文件用于从旧版本升级，不因最终表被删就能直接移除。没有重建基线与升级策略时，不应压平 Alembic 链。

## 4. 可以清理的负担及条件

### A1. 过时的“重复计划修复”脚本：应优先移出可执行工具目录

- 证据：`backend/scripts/fix_duplicate_plans.py` 按学员只保留最新 ACTIVE，其余标记 SUPERSEDED；提交历史在 `89f55df` 可见。`96034a1` 已明确允许最多三份 ACTIVE；当前评分服务仍按该政策生成计划。
- 判断：旧问题定义已失效。多份活动计划现在是合法状态，执行旧脚本反而破坏产品规则。
- 移除方式：归档为只读历史材料或删除运行脚本，同时移除运行指引；不执行它来“验证”，不更改现有计划。
- 验收：同一用户存在两至三份活动计划时仍完整可见；第四份按当前归档规则处理。

### A2. 视频路由的未使用导入、四维页面的五列 CSS：可直接做小补丁

- `backend/app/features/video/router.py:21` 附近仍导入 `analyze`、`analyze_video`、`create_voice_session`，但该路由已改为创建后台任务，实际分析发生在 tasks service。迁移来源是 `7b268d6`。
- `frontend/src/components/report/ScoreEvidencePanel.vue:89` 仍为 `repeat(5, ...)`，实际只有四个维度；四维决策来源为 `1ba30cd`。
- 移除方式：删未使用导入、将网格按四维调整。只删残留，不连带删视频分析能力。
- 验收：模块导入、后端相关测试、报告四个标签与桌面布局检查。

### A3. 五维时代的“得体性”实时计算：可停止计算；数据库暂不能直接删

- `backend/app/features/evaluations/service.py:533` 仍计算得体性，`:451` 仍接受该维度的新增证据。schema 已将其排除出公开四维分数，正式资格只认四维。
- 判断：实时规则计算与新证据接收是无效工作，可以去除；旧数据库字段则承担兼容职责。
- 本地仍有 28 条 appropriateness 证据，不是空壳。若最终删除列，需决定历史导出保留方式、迁移新写入默认值、更新 schema 与所有构造点，再单独做数据库迁移。
- 不建议为了少一个字段而先破坏旧报告可读性。

### B1. 只写不读的训练状态缓存：高收益、可分阶段移除

- `backend/app/infrastructure/state_store.py:42` 提供 get，但当前业务代码没有 get 调用；读取只出现在删除/退出测试。
- `training/service.py:145`、`:453` 写入 stage、roundNo 等，恢复训练实际从 SQL 读取。历史 `git log -S 'state_store.get' -- backend/app` 未发现业务读调用的增删记录；初始提交已有该缓存结构。
- 判断：至少当前它不是必需的会话恢复机制。把它视为为缓存恢复预留的架构层是推断，不能据此声称当时已经实现 Redis 恢复。
- 移除范围：训练状态写入与清理、state_store 的生命周期、ready 中 sessionState 的要求、相关专门测试。Redis 限流在独立 rate_limiter 中，必须保留。
- 验收：训练、重启后 SQL 读取、退出、删除、限流与生产就绪检查均正常；不应再因无业务用途的 sessionState 缓存异常使 ready 失败。

### B2. 旧“上传录像 → 排队分析”链路：具备下线条件，但先确认 API 使用方

- `e498bb0` 引入录像上传；`7b268d6` 将耗时分析改为队列。`a95097a` 明确去掉录答模式，改为实时房间。
- 当前前端业务源码不再请求 `/video-interviews`；实时房间经 `/voice/sessions` 保存。旧路由仍注册，任务 worker 仍在启动阶段运行。
- `backend/app/features/tasks/service.py:177` 的 HANDLERS 只有 VIDEO_INTERVIEW。当前本地任务表有 5 条 DONE、1 条 FAILED，未发现 PENDING/RUNNING。
- 判断：不是通用任务平台的必要核心，而是旧产品流程的遗留；但仍存在公开端点、管理页及历史任务，因此不是“无引用文件”。
- 下线顺序：确认其他部署和外部调用 → 停止新建旧任务 → 处理残留任务 → 停 worker、移除旧入口与专属管理 UI → 保留历史结果与录像读取。最后再决定是否删除任务表。
- `_split_turns` 当前被 worker 反向导入，不能先删路由文件再发现 worker 启动失败。
- 验收：实时文字/语音/视频完整链路、录制回放、按题切片、历史任务读取与注销。

### B3. 无作答时伪造两轮占位回答：应随旧管线下线，或改成独立无评分结果

- `d5bb175` 的补丁明确引入 `_degraded_turns`，目的是让静音视频仍能留录像、出报告，绕过当时“两轮才可评分”的限制。
- 位置：`backend/app/features/voice/session.py:17`、`:21`；当前仍由旧 worker 在转写为空时调用。
- 新规则已允许一轮总结，零作答不生成空报告；原来的轮数绕过已与新规则冲突。
- 不应只把两轮改成一轮：占位串依旧不是用户回答。若保留上传分析，应保存录像与镜头观测，明确“无可评分作答”，不创建伪造的用户发言。
- 风险推断：若大模型成功为占位文本给出四维引用，现有逐字证据校验未必识别其非用户作答身份。未做真实模型调用，不宣称已复现此路径。

## 6. 架构上的后续问题

1. **有效评分口径尚未完全贯通推荐。** 新看板与报告通过 `evaluations/quality.py` 统一资格，但 `plans/personalization.py` 的 scene_average 和 `scene_fit.py` 的 historical_fit 仍直接汇总 Evaluation。适合复用“评分有效性”条件，不能机械要求所有推荐都使用看板的同条件分组。
2. **读时兼容层承担迁移职责。** normalized_tasks 查询最近训练、补课程、推断来源甚至补复测任务。应给任务 JSON 增加版本并做明确升级，读请求最终只做校验与序列化。前述 14 条依赖计划 baseline 补足来源的数据，是不能立即删兼容层的实证；回退到最近训练仍属应取消的潜在不确定性。
3. **结构文档已落后于实现。** architecture.md 仍说 useTrainingSession 读取 SSE；当前组合式函数请求 messages/complete，SSE 作为另一个端点保留给流式客户端与压测。应更新文档，不能据此直接删 SSE。
4. **最近设计没有进入 Git。** 评分资格、重评版本、退出丢弃等重要语义依赖未跟踪文件；仅克隆 HEAD 无法复现当前系统。先按功能拆分提交并检查迁移与测试纳入范围，比继续新增功能更有价值。本次没有擅自提交。
