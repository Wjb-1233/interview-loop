## 六轮完整问答

### 第 1 轮

**面试官：** 你提到“使用事务及带剩余名额条件的原子更新防止超卖”，请具体说明该更新语句的写法与事务边界，并分析并发下若更新影响行数为0时接口如何返回、如何避免重复扣减？

**演示作答：** 这份经历是功能验收的虚构示例。报名接口里我在同一个数据库事务中，先执行 UPDATE activity SET remaining = remaining - 1 WHERE id = :activity_id AND remaining > 0，检查影响行数，再插入报名记录，最后提交。影响行数为零时会先确认活动是否存在，不存在返回404，名额已满返回409。报名表对活动ID和用户ID设联合唯一约束；同一个人重复请求触发唯一键冲突时，整个事务回滚，扣减名额也撤销，然后查询已有报名记录并返回已有结果，因此不会重复扣减。这里没有把Redis当成最终的名额依据。

### 第 2 轮

**面试官：** 你说影响行数为0时先确认活动是否存在，这个“确认”是否在同一个事务、同一隔离级别下执行？并发下活动刚被删或名额刚被释放，你怎么保证返回404/409不误判？

**演示作答：** 演示版本是在同一个事务里补查，但我没有专项验证并发删除和释放名额这两种时序，因此不能保证404和409的分类始终准确。我的改进方案是对活动状态使用SELECT FOR UPDATE当前读，删除、释放和报名都遵循同一行的锁定规则，再根据锁定时看到的状态判断；如果发现名额已经释放，就回滚后按同一用户和活动身份做一次受控重试，仍由唯一约束保证幂等。404或409只表示本次处理时观察到的结果，不能承诺客户端收到响应后状态永远不变。这些改进还需要补并发用例验证。

### 第 3 轮

**面试官：** 好，假设线上接口突然变慢，你会怎么一步步定位问题？结合这个报名项目说说你的实际排查路径。

**演示作答：** 我会先确认是所有接口还是报名接口变慢，区分吞吐、P95耗时和错误率，再看最近发布与数据库连接、锁等待。这个虚构项目里，我实际做的是在同一台测试机用200并发复现，给请求及SQL记录耗时，发现活动展示信息被重复查询；再用EXPLAIN检查访问路径，补适合查询条件的索引，并把低频变更的展示内容放进Redis。相同数据和并发下，P95从约680毫秒降到210毫秒。但因为索引和缓存是一起调整的，这次结果不能分别证明每项优化贡献多少，我会再分别开关做对照。线上如果出现大面积超时，应先回滚或限流止损，而不是直接扩大连接池。

### 第 4 轮

**面试官：** 你提到索引和缓存一起改，无法拆分贡献。如果只允许先上一项，你会先上哪个？依据是什么，怎么验证它单独有效？

**演示作答：** 我会优先处理已经定位到的慢SQL索引问题，前提是执行计划确认扫描行数高、现有索引没有覆盖主要筛选条件。原因是这样不引入缓存一致性和失效策略，变更点更少，但要评估索引空间、写入成本和上线DDL风险。验证时先记录基线，再只修改索引，保持同一机器、数据量、并发、预热方式和压测时长，比较扫描行数、P95、吞吐及错误率，重复几轮而不只挑最好的一轮。确认单项结果后，再单独打开展示缓存做第二组实验。原演示数据只证明组合优化有效，目前没有单项实验结果，我不会把680到210毫秒全部归功于索引。

### 第 5 轮

**面试官：** 请具体说一个你上线后出过的故障：怎么发现、怎么止损、事后改了什么？

**演示作答：** 我还没有真实生产环境的故障处理经历，不能把测试问题包装成上线事故。这份演示项目能说明的是：测试里发现接口慢，我通过请求日志和SQL耗时缩小范围，再做索引和展示缓存的改进，并准备补单项对照实验。真正线上出故障时，我会先确认影响范围，必要时回滚或限流止损，保留日志，再定位原因，最后补监控和回归用例。但这只是我计划采用的流程，我没有亲自完成过生产告警处置和回滚演练，目前也不能给出已经验证过的告警阈值。

### 第 6 轮

**面试官：** 理解，不编造经历这点很好。那回到可验证的范围：测试中你如何确认“没有超卖”？请给出具体校验SQL和并发下可能漏检的场景。

**演示作答：** 以初始100个名额、没有取消操作的单活动用例为例，我会等并发请求与数据库事务结束，再在主库的一致性快照里校验：SELECT COUNT(*) AS booked, COUNT(DISTINCT user_id) AS users FROM registration WHERE activity_id = :id；再查 SELECT remaining FROM activity WHERE id = :id。要求booked不超过100、booked等于users、remaining不小于0，而且booked加remaining等于初始名额。接口200的次数不能直接当成报名人数，因为幂等重试也可能返回成功。最终快照仍可能漏掉短暂超卖后又被补偿的情况，所以还要检查扣减事务逻辑，补重复请求、超时重试和事务回滚的并发用例，并关联每次提交与日志。演示目前只核验过最终数据；取消、退款和活动删除没有覆盖，我不能据此承诺所有场景都没有超卖。
