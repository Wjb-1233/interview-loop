## 六、建议（按收益排序）

1. **先拆 `evaluate_session` 与 `complete_training_task`。** 这两处同时是高分险与高频路径：建议按「取数与校验 → 组 prompt → 模型调用与容错 → 落库 → 计划副作用」切成 4–5 个纯函数，主函数只保留编排；拆完再补一条回归用例覆盖降级分支。
2. **语言链路抽共性。** `stream_reply`、`create_training_session`、`evidence_reply` 都在重复「取上下文 / 记轮次 / 判结束」，抽成一个上下文装配器后三处复杂度会同步下降。
3. **统计与快照类可表驱动。** `assessment_snapshot`(47)、`study_inputs`(42)、`dashboard_data`(35)、`analyze_calibration`(33) 多是字段分派，换成字段表 + 小函数比继续加分支更稳。
4. **迁移与归档脚本低优先。** 它们不在请求路径上，可等下次动这些脚本时顺手拆。
5. **把阈值纳入 CI。** 当前规则只产出提示；建议在 `backend/tests` 之外加一个“复杂度不得超过现值”的回归门，避免复杂度回涨。

## 七、覆盖与限制

- 只跑了 Python 适配器：前端 59 个 TS 文件、Vue 组件与 e2e 用例未纳入依赖图。
- 模块分组到 `depth=2` 只有 4 组、组间边为 0，因此“无环”只在这个粒度上成立；`backend/app` 内部各 feature 之间没有单独判环。
- 静态分析不等于运行时：并发、时延、外部服务（DeepSeek / 豆包 / Simli）行为都未验证。
- 图外的 7 条线索说明架构图覆盖的是主链路，不是全部代码。
